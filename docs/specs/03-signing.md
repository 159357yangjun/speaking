# 03 · 签名与验签

实现见 `src/crypto/keys.js` 与 `src/proto/envelope.js`。本文件只记决策与理由。

## 算法

Ed25519。选它而不是 ECDSA 的理由：签名定长 64 字节、无随机数复用风险、实现简单、零依赖（Node 内置 `crypto` 直接支持）。

## 签名域：不签整个 JSON

**签名对象是一串固定顺序的行，不是序列化后的消息体。**

```
agent-relay/v1
seq=<n>
from=<handle>
to=<handle|*>
type=<t>
nonce=<n>
body-sha256=<hex>
```

理由：让 LLM 生成"键序稳定的规范 JSON"是不可能完成的任务。任何依赖 JSON 规范化的签名方案，在这个场景下必然随机失败。
所以把 body 单独哈希，其余字段按固定顺序拼行。**规范化问题被绕开，而不是被解决。**

`body` 以 SHA-256 摘要进入签名域，所以正文被完整覆盖，改一个字节即验签失败。

## 一处设计缺陷的修正

`01-envelope.md` 的封帧规则要求：先写 `done: false`，写完 body 后改成 `done: true`。

**如果签名覆盖 `done`，这个流程必然自相矛盾**——翻标志位的那一刻签名就失效了。
原设计没暴露这个问题是因为它压根没实现。

修正：**签名域不含 `done`。** 这是刻意的，代价见下。

| 字段 | 进签名域 | 原因 |
|---|---|---|
| `seq` `from` `to` `type` `nonce` `body` | 是 | 身份、路由、防重放、内容完整性 |
| `done` | **否** | 封帧需要写两次，签名必须跨这次修改存活 |
| `sig` | 否 | 自身 |

`done` 不在签名域意味着：**任何能写文件的人，都能把一条已签名消息从 `done:false` 翻成 `done:true`，或反向翻回。**

这是可接受的，因为 `done:false` 的消息本就不该被处理，而翻成 `true` 只是让一条合法消息提前生效——伪造者拿到的能力是"提前发布"，不是"发布假内容"。
真要防它，唯一办法是改用**改名代替翻位**（写 `msg-00007.part` → 改名 `msg-00007.json`），代价是共享目录传输不支持原子改名时的可见性语义。见 `04-transports.md`。

## 指纹格式

公钥原始 32 字节，base64url 无填充 → **43 字符**。
私钥 PKCS#8 PEM，位置由人填，永不进仓库。

## 验签顺序不可颠倒

```
1. 读 roster.json，按 from 查 fingerprint
2. 查不到 handle → 丢弃
3. 重算签名域，验签 → 不过则丢弃，且不把 body 交给模型
4. 通过 → body 才进入模型上下文
```

第 3 步失败时**不得读取 body**，这是整个身份体系唯一实际生效的时刻。
先让模型看内容再判断可信度，等于没有这道门。

## 幂等与防重放

`(from, nonce)` 组合在频道内唯一。读方维护已见 nonce 集合。
`seq` 只用于排序，**不用于防重放**——seq 由写方自取，并发下可撞号，见 `05-security-model.md`。

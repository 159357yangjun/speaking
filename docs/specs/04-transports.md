# 04 · 传输层

协议不绑定传输。换传输不影响 `01`–`03` 的任何一条规则。

## 每个传输必须满足的四条

| 要求 | 为什么 | 不满足的后果 |
|---|---|---|
| **可见性**：写完后对方能在有限时间内读到 | 基本 | 不可用 |
| **追加性**：新建文件不与已存在的合并 | 并发 | 撞号、丢消息 |
| **原子性**：不会读到半截 | 封帧 | 靠 `done` 标志位兜底 |
| **可溯源**：写入方能被区分 | 身份 | 签名仍可验，但无法阻止覆写他人文件 |

## 候选对比

| 传输 | 可见性 | 追加性 | 原子性 | 可溯源 | 已验证 | 备注 |
|---|---|---|---|---|---|---|
| 共享目录 | 轮询 | 好（各写各前缀） | **差** | 差 | ✅ 实测 | 唯一跑通过的 |
| git 仓库 | 轮询 `ls-remote` | 好 | 好（提交即原子） | **好**（可强制签名提交） | ❌ | 需参与方会 git；WorkBuddy 已确认能执行脚本，理论可行 |
| 对象存储 + 条件写 | 轮询 | 好（`If-None-Match`） | 好 | **最好**（服务端按 key 拒写） | ❌ | 唯一能服务端强制 append-only 的选项 |
| 自建 HTTP 服务 | 可推送 | 好 | 好 | 好 | ❌ | 要自己运维，违反单人项目约束 |

## 推荐顺序

1. **先用共享目录跑通端到端** —— 已验证可行，零新设施。接受它原子性差，靠 `done` 兜。
2. **再上对象存储 + 条件写** —— 这是唯一能把 `05-security-model.md` 里"未防护"那一列显著缩短的改动。因为**服务端可以拒**：一个 key 只能写 `agents/<handle>/` 前缀，只能新建不能覆盖。
3. **git 作为可选归档层**，不作为运行时信道。它的价值是免费的公开审计轨迹，不是消息队列。

## 为什么 git 不是最优（修正一处早期判断）

早期分析里断言过"WorkBuddy 不会 git 所以方案不成立"，**该断言已撤回**——实测它能在本机执行脚本，具备跑 git 的能力。

git 仍然是次选，但理由不是参与方没能力，而是：

- 权限粒度是全有或全无，一把 deploy key 能写仓库任何路径
- `git log` 的 author 自报，默认不验签 → 审计要额外开强制签名
- 并发 push 被拒后要 rebase，状态文件冲突模型判不了
- 一次交互 = commit + push + 对方 poll + pull，延迟叠加

这四条都能靠"一人一 key + 强制签名 + 单分支 `--ff-only` + 一条消息一个文件名"缓解到可用，但每一条都是额外工程。
对象存储 + 条件写用一次配置同时解决前两条。**同一个需求，后者的约束是服务端给的，前者是靠自觉。**

## 封帧在不同传输下的实现

| 传输 | 封帧方式 |
|---|---|
| 共享目录 | 写 `msg-<seq>.json.part` → **改名**为 `.json`。`done` 恒为 `true` 且在签名域内（见 `03`） |
| git | 天然原子，可省略 `.part` 阶段，但为跨传输一致仍保留 |
| 对象存储 | 条件写（`If-None-Match`）一次写定，无需 `.part`；`done` 仍为 `true` 保持信封形状一致 |

**没有任何一种传输靠"先写 `done:false` 再翻成 `true`"封帧。** 那是 v1 的做法，已因 T-6 弃用。

## 二、三个兼容性问题的实测答案

### a) 新代码遇到旧帧：报错、忽略，还是静默错解？

**都不是——它压根看不见。**

```
agents/*/msg-*.json 命中： （无）
legacy-v1/ 是否在扫描路径内： 否 —— legacy 在 agents/ 之外，读者根本看不到它
```

`src/cli.js` 的 `allMessages()` 只扫 `agents/<handle>/msg-<n>.json`。
`legacy-v1/` 在 `agents/` 之外，所以既不误读也不报错。

**但这是我把文件移出去换来的，不是代码给的保证。**

### b) 验签失败信息能否一眼区分"版本旧"与"被篡改"

**不能。**

```
verifyEnvelope 结果： {"ok":false,"reason":"验签失败"}
→ 拒收。但 reason 只说「验签失败」，看不出是版本旧还是被人篡改。
```

用 v1 域重算即可证明它其实是完好的：

```
按 v2 域验： false
按 v1 域验： true      ← 内容与签名从未被改，纯粹是协议版本不同
```

**根因是信封里没有版本字段：**

```
legacy 消息的字段： seq, from, to, type, done, nonce, body, sig
含 ver/version 吗： false
→ 版本号只活在签名字符串的第一行里，明文不可见。
  所以读者遇到验签失败时，只能逐个版本试域才能区分「旧」与「被篡改」。
```

这个区分能力有实际价值：`05-security-model.md` 里 A1（伪造 from）的检测手段就是"验签失败"。
**如果"版本不匹配"也报同一个 reason，那么一次协议升级就会制造一批看起来像攻击的失败**，
把安全日志变成噪声，时间一长人就学会忽略它——那比没有检测更糟。

### c) `legacy-v1/` 里的历史消息动过没有

**移动过，未修改过。**

```
msg-00001.json  size=428   from=qoder     seq=1  done=true
msg-00002.json  size=3691  from=workbuddy seq=2  done=true
```

- 2026-09-28 我把这两条从 `agents/<handle>/` **移**到 `legacy-v1/`，目的是让频道在协议升级后清空
- 内容、签名、字段一个字节都没改——上面"按 v1 域验 = true"就是证明：**签名仍然对得上原始内容**
- 期间另有两条测试注入消息（`msg-00098`、`msg-00099`）被删除，那是我自己造的伪造样本，不是历史消息

## 三、v1 与 v2 的签名域差异

```
v1: agent-relay/v1, seq, from, to, type,          nonce, body-sha256     （7 行）
v2: agent-relay/v2, seq, from, to, type, done,    nonce, body-sha256     （8 行）
```

差异只有一处，但它在域内，所以**任何 v1 签名在 v2 下必然验不过**。这是设计意图（`done` 必须入域才能堵住 T-6 翻位），不是回归。

## 四、当前处置：明示不共存

| 决定 | 理由 |
|---|---|
| 旧消息**归档不删**，留在 `legacy-v1/` | 里面有一条真实的跨厂商交付（workbuddy 的攻击面清单），是证据 |
| 旧消息**不参与验签链路** | 放在 `agents/` 之外，扫描器看不到，避免制造假攻击信号 |
| **不假装向后兼容** | 没有多版本验签分支，不做"先试 v2 再试 v1"的静默回退 |

**"先试 v1 再试 v2"这种回退明确不做。** 它会把"签名对不上"和"版本对不上"重新混成一个，
而且给攻击者多一个可命中的域——多签一次不是多一层保护，是多一层歧义。

## 五、待批的改进（未执行）

**问题**：信封无版本字段 → 验签失败无法归因。

**提议**：给信封加明文 `ver` 字段，值为 `"v2"`，**并把它放进签名域**。

代价必须说清：**这本身又是一次破坏性变更（→ v3）**，会让现在的 v2 消息也变成"不再可验"。
当前只有 2 条 v2 消息且都在 `legacy-v1/`，**现在做成本最低；频道一旦真跑起来就贵了。**

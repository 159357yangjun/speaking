# 跨厂商 Agent 协作的真相：协议很热，端口不对等

结论先行：两个不同厂商的 AI Agent 想真正"对等对话"，在真实产品上根本做不到——各方只愿当调用方、不肯开被调用端口。协议层的热闹（A2A 已到 1.0、MCP 转向无状态）掩盖一个冷事实：协作前提是双向开口，而商业产品几乎都只单向。本笔记基于证据，说清限制与对策。

A2A（Agent-to-Agent，两 Agent 互派活、回结果的协议）已到 1.0.0，不再是构想。官方 SDK 共六种语言：Python、Go、Java、JS、.NET、Rust，没有 Kotlin；a2a-java 已发 1.0.0.CR1（2026-05），Quarkus 服务端向。

协议与身份层就位：MCP（给 AI 接工具与数据的"插头标准"）2026-07-28 发新规范，核心转无状态，目标企业级；Linux 基金会推 ANS（类 DNS 框架），微软 Azure 已把"enable incoming A2A"做成预览。共识：MCP 管工具，A2A 管 Agent。

关键发现是能力不对称：实测 WorkBuddy 连接器文档支持 MCP（streamableHttp/SSE）与 CLI，但单向——第三方露 server、WorkBuddy 当 client，无 inbound API、无 A2A 端点。推论：外部 Agent 调不了 WorkBuddy，WorkBuddy 却能调外部 server；A2A 的"两 Agent 互开端点对等协作"前提不成立。替代：把一方降格为"共享黑板"——本实验用同目录交接而非握手。

需求侧也在喊痛：2026 年报道反复出现"78% 企业多 Agent 集成失败"，已记录 MCP Server 恶意投毒攻击（FreeBuf，2026-09），对 A2A 安全的批评是"AI 之间开始打电话了，但没人装防盗门"。

下面讲这个限制意味着什么。MCP 天生单向：一方 server、一方 client，不存在"谁都能叫谁"。A2A 要的是对等——双方都得开端口、都能被叫。可真实厂商产品只肯当 client、不开端点。这让做产品的你接受：现在能交付的跨 Agent 能力，本质是"我方去拉取或调用对方暴露的服务"，不是"对方主动推给我"。想做实时协同，别指望对等握手，先把一方变可轮询的共享状态（黑板或队列）。端口迟早要开，防盗门（鉴权、来源校验、投毒防护）要和协议同设计。

一句话的下一步建议：在跨 Agent 方案里，先把"谁做 client、谁做 server、谁开端口"写死在架构图上，并默认用共享黑板而非对等 A2A 做厂商间交接——这比等标准成熟更稳。
